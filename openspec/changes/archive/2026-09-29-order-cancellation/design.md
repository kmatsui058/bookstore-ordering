## Context

注文の状態と遷移は、契約リポジトリのドメインモデル（集約ルート「注文」`bkst_ordr_ordm_ord`、ステートマシン `bkst_ordr_ordm_ord_state`）で決まっている。注文 API の定義（`/orders/{orderID}/cancel`）も契約リポジトリにすでにある。このリポジトリは、注文をイベントの列（イベントソーシング）で保存し、読み取り用のスナップショットを別に持つ。

## Goals / Non-Goals

**Goals:**

- 「キャンセルできるのは出荷前だけ」というルールを集約の中だけで守る
- キャンセルが成功したときだけ注文キャンセル（OrderCancelled）を保存・公開する

**Non-Goals:**

- 請求コンテキストでの注文キャンセルの扱い
- キャンセルの理由の記録（モデルに語がない）

## Decisions

### D1: キャンセルできるかどうかは集約「注文」が判断する

**決定**: 出荷前（受付済み・確定）かどうかの判定を集約のコマンド `Cancel` に置き、アプリケーション層やハンドラーには置かない。判定は注文ステータスの網羅的な switch で書く。

**理由**: ルールを1箇所に置けば、API 以外（将来のバッチやイベントの購読）からキャンセルしても同じルールが効く。網羅的な switch にしておけば、注文ステータスに値を足したときに、キャンセルできるかどうかの判断漏れを lint で見つけられる。

**検討してやめた案**: ハンドラーで状態を見て弾く → ルールが API の中に閉じ込められ、ほかの入口から迂回できる。

### D2: 断ったときはイベントを発行せず、状態のエラーとして返す

**決定**: キャンセルできない状態なら、集約は注文キャンセルを発行せずに「いまの状態ではできない」種類のエラー（`ErrNotCancellable`。`ErrInvalidState` を包む）を返す。API はこれを 409 に、注文が見つからないときは 404 に変換する。

**理由**: 状態のエラーと入力のエラーを型で分けておけば、ハンドラーはエラーの種類だけを見てステータスを選べる。409 と 404 は契約リポジトリの API の定義にすでにある。

**検討してやめた案**: すでにキャンセルした注文へのキャンセルを成功として扱う（冪等にする） → specs で「もう一度はキャンセルできない」と決めたので採らない。同じ注文キャンセルが重ねて記録されることもない。

### D3: 永続化と公開は既存のコマンドと同じ流れに乗せる

**決定**: 集約をイベントの列から復元 → `Cancel` → 注文キャンセルを追記しスナップショットを保存 → コミットのあとで公開、という既存の流れをそのまま使う。

**理由**: 新しい仕組みを足さずに済む。読み込んだあとに同じ注文が別の処理で変わった場合（たとえば同時に出荷済みにされた場合）は、楽観的並行性制御でコミットが衝突として失敗するので、出荷済みの注文がキャンセルされることはない。

## Risks / Trade-offs

- [公開に失敗すると、キャンセルは保存されたのに他のコンテキストに伝わらない] → 公開の再送の仕組みがないことをコードの TODO に残し、実際のメッセージ基盤につなぐときに入れる
